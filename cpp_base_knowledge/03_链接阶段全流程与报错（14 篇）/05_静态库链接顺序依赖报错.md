# 静态库链接顺序依赖报错

## 一、前言

`undefined reference` 里有一类最冤的情况：库明明存在、符号明明在库里，**只是命令行顺序写反了**。

核心总纲：**链接器对静态库是单遍从左到右扫描，依赖方必须写在被依赖方前面。** 因为扫过的库不会回头重扫，写反了就没人再解析前面引入的未定义符号。

## 二、底层机制

### 1. 归档扫描算法

链接器处理静态库的过程：

1. 从左到右遍历命令行参数；
2. 维护一个"当前未定义符号集合 U"；
3. 遇到 `.o`：直接加入，定义符号从 U 中移除，未定义符号加入 U；
4. 遇到 `.a`：扫描成员，**只抽取能定义 U 中符号的成员**；抽取后更新 U，继续扫描该归档；
5. 处理完一个归档后，**不会再回头重新扫描它**；
6. 全部结束后 U 非空 → `undefined reference`。

### 2. 顺序规则

假设：

```text
main.o 调用 foo()
libfoo.a 中的 foo() 调用 bar()
libbar.a 中定义了 bar()
```

正确的顺序是"使用者 → 被使用者"：

```bash
gcc main.o -lfoo -lbar -o app
```

- 扫 `-lfoo` 时，U 中有 `foo`，抽取 `foo.o`，引入 `bar`；
- 扫 `-lbar` 时，U 中有 `bar`，抽取 `bar.o`，解析完成。

反过来的错误顺序：

```bash
gcc main.o -lbar -lfoo -o app
```

- 扫 `-lbar` 时，U 中只有 `foo`，`bar` 没人要，归档不抽取；
- 扫 `-lfoo` 时，抽取 `foo.o`，引入 `bar`，但 `-lbar` 已经扫过，不会回头；
- 最终 `bar` 仍未定义 → `undefined reference to 'bar'`。

### 3. 对象文件与库的顺序

对象文件通常应放在库前面：

```bash
gcc main.o util.o -lfoo -lbar -o app    # 推荐
gcc -lfoo main.o -o app                 # main.o 的符号引用在扫库之后才出现，可能失败
```

### 4. 循环依赖

两个静态库互相引用时，任何线性顺序都不够，需要让链接器反复扫描整组库：

```bash
gcc main.o -Wl,--start-group -lfoo -lbar -Wl,--end-group -o app
```

`--start-group` / `--end-group` 之间的归档会被反复扫描，直到没有新的未定义符号可以解析，代价是链接变慢。

## 三、高频场景

### 1. 库写在对象前面

```bash
gcc -lfoo main.o -o app    # 错误
gcc main.o -lfoo -o app    # 正确
```

### 2. 依赖链顺序颠倒

```bash
# A 依赖 B
gcc main.o -lA -lB -o app    # 正确
gcc main.o -lB -lA -o app    # 错误
```

### 3. 系统库放在错误位置

`-lm`、`-lpthread`、`-ldl`、`-lstdc++` 也是库，同样受顺序影响。习惯上放在命令行最后：

```bash
gcc main.o -lfoo -lm -lpthread -ldl -o app
```

### 4. pkg-config 输出顺序

`pkg-config --libs foo` 输出的顺序是库自己声明好的依赖顺序，通常可以直接用：

```bash
gcc main.o $(pkg-config --libs foo) -o app
```

不要手工把输出顺序打乱。

### 5. CMake 项目

`target_link_libraries(app PRIVATE foo)` 会依据 target 的依赖关系自动排序，通常不需要手工调整。手工 `link_libraries` 混合绝对路径时，顺序问题仍可能出现。

### 6. --whole-archive 的场景

某些库依赖"只要链进来就自动注册"的静态初始化（插件注册表、测试框架）。这时需要强制抽取全部成员：

```bash
gcc main.o -Wl,--whole-archive -lregistry -Wl,--no-whole-archive -o app
```

`--whole-archive` 后必须跟 `--no-whole-archive`，否则后续所有库都会被整包塞入，容易引发 multiple definition。

## 四、排查流程

### Step 1：确认报错符号在哪个库

```bash
for f in *.a; do
  nm -C --defined-only "$f" | grep -q ' foo$' && echo "$f"
done
```

### Step 2：查看链接器实际扫描了哪些成员

```bash
gcc main.o -lfoo -lbar -Wl,-Map=link.map -o app
grep -n "libfoo.a\|libbar.a" link.map
```

### Step 3：跟踪某个符号的解析过程

```bash
gcc main.o -lfoo -lbar -Wl,--trace-symbol=bar -o app
```

输出会显示符号在哪个文件被定义/引用。

### Step 4：验证顺序假设

把可疑库移到命令行末尾或使用 `--start-group` 重试，如果报错消失，基本可以确认是顺序问题。

### Step 5：检查是否根本没链接库

```bash
gcc -### main.o -lfoo -o app 2>&1 | tail   # 看实际传入 ld 的参数
```

## 五、命令速查表

| 目的 | 命令 |
|---|---|
| 查看库中符号 | `nm -C --defined-only libfoo.a` |
| 查看未定义符号 | `nm -u -C main.o` |
| 跟踪符号解析 | `-Wl,--trace-symbol=foo` |
| 生成链接 map | `-Wl,-Map=link.map` |
| 解决循环依赖 | `-Wl,--start-group ... -Wl,--end-group` |
| 强制整包链接 | `-Wl,--whole-archive -lfoo -Wl,--no-whole-archive` |
| 查看真实链接命令 | `make V=1` / `gcc -###` |

## 六、预防规范

1. 链接命令统一按"对象文件 → 业务库 → 基础库 → 系统库"排列。
2. 静态库依赖关系保持单向；出现循环依赖先考虑重构，实在不行用 `--start-group`。
3. 优先使用 CMake 的 `target_link_libraries` 和 pkg-config，不手工拼库顺序。
4. 不要在对象文件之前写 `-l`。
5. 慎用 `--whole-archive`，使用时必须成对出现。
6. 把链接命令写进构建脚本，避免手工命令与 CI 不一致。

## 七、面试标准简答

### 1. 为什么静态库对顺序敏感？

链接器对归档是单遍从左到右扫描：处理某个归档时，只解析当前尚未定义的符号，处理完不再回头。因此，引入新未定义符号的库（依赖方）必须写在提供这些符号的库（被依赖方）前面；顺序相反时，被依赖方已经扫过，不会再解析依赖方后来引入的符号。

### 2. 循环依赖怎么解决？

用 `-Wl,--start-group` 和 `-Wl,--end-group` 把相关静态库包起来，让链接器反复扫描，直到没有新的符号可解析。更根本的做法是拆分库、消除循环。

### 3. --whole-archive 有什么用？

强制抽取静态库的全部成员，而不是按需抽取。适合依赖静态初始化注册的库（插件、测试框架）。它会增大体积并增加符号冲突风险，必须配合 `--no-whole-archive` 使用。

### 4. 对象文件和库的顺序有要求吗？

有。对象文件应放在库前面，保证它引入的未定义符号在扫描库时已经存在。把 `-l` 放在 `.o` 前面可能让库被跳过。

## 八、极简口诀

**静态库单遍扫，扫过不再回头找；**

**使用者在前面，被依赖者放后边；**

**循环依赖 start-group，整包链接 whole-archive；**

**对象在前库在后，系统库排最后。**
