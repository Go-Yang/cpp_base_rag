# 动态库.so/.dll 依赖缺失报错

## 一、前言

有一类问题最让人困惑：**编译链接全都成功，程序一运行就报找不到动态库**。

```text
error while loading shared libraries: libxxx.so: cannot open shared object file: No such file or directory
```

Windows 上对应"找不到 xxx.dll"、错误码 `0xc0000135` 或 `LoadLibrary` 返回 126。

核心总纲：**链接成功只证明"链接时找得到"，运行成功还要求"加载时找得到 + 符号对得上 + 版本兼容"。** 这是两套独立的查找机制。

## 二、Linux 动态库查找机制

### 1. 依赖从哪来

可执行文件/共享库的 `.dynamic` 段里记录了 `DT_NEEDED` 条目，存的是依赖库的 **SONAME**（如 `libfoo.so.1`），不是完整路径。

```bash
readelf -d app | grep NEEDED
```

### 2. 动态链接器搜索顺序

`ld.so` 按以下顺序查找 `DT_NEEDED` 中的库：

1. **DT_RPATH**（旧式 rpath，如果存在且未启用 RUNPATH）；
2. **LD_LIBRARY_PATH** 环境变量；
3. **DT_RUNPATH**（新式 runpath）；
4. `/etc/ld.so.cache`（由 `ldconfig` 生成，来自 `/etc/ld.so.conf.d/*.conf`）；
5. 默认目录：`/lib`、`/usr/lib`、`/lib64`、`/usr/lib64`（以及发行版配置）。

注意 RPATH 和 RUNPATH 的区别：

- `DT_RPATH` 先于 `LD_LIBRARY_PATH`；
- `DT_RUNPATH` 后于 `LD_LIBRARY_PATH`，且**不作用于间接依赖**（只对直接依赖生效）；
- 现代链接器默认生成 RUNPATH（`--enable-new-dtags`）。

### 3. SONAME 与文件名的关系

```bash
objdump -p libfoo.so.1.0 | grep SONAME   # 例如 SONAME libfoo.so.1
```

运行时只认 SONAME。只有 `libfoo.so.1.0`、没有 `libfoo.so.1` 这个符号链接时，加载器就找不到。安装库时通常由 `ldconfig` 自动维护这些链接。

## 三、Windows DLL 查找机制

Windows 加载器按大致以下顺序查找 DLL：

1. 可执行文件所在目录；
2. 系统目录（`C:\Windows\System32` 等）；
3. 当前工作目录（受安全设置影响）；
4. `PATH` 环境变量中的目录。

常见坑：

- 开发机把 DLL 放在 `PATH` 里能跑，拷到客户机器就缺；
- 依赖的 VC 运行库（`msvcp140.dll`、`vcruntime140.dll`）未安装；
- 32/64 位 DLL 混用，报"不是有效的 Win32 应用程序"。

## 四、高频根因与修复

### 1. 库根本没安装

```bash
ldconfig -p | grep libfoo
apt list --installed | grep libfoo
```

修复：安装对应运行库包（不只是 `-dev` 包）。

### 2. 装了但不在搜索路径

```bash
find / -name 'libfoo.so*' 2>/dev/null
```

修复手段按推荐顺序：

1. **RPATH/RUNPATH 指向相对路径**（推荐，随程序分发）：

```bash
gcc main.o -L./lib -lfoo -Wl,-rpath,'$ORIGIN/../lib' -o app
# 注意用单引号，避免 shell 展开 $ORIGIN
```

2. 写入 `/etc/ld.so.conf.d/foo.conf`，再执行 `sudo ldconfig`（系统级安装）；
3. 临时用 `LD_LIBRARY_PATH=/path ./app`（只适合调试）；
4. 用 `patchelf --set-rpath` 修改已有二进制的 RUNPATH。

### 3. 只有链接名，没有 SONAME 链接

```bash
ls -l /usr/lib/x86_64-linux-gnu/libfoo.so*
# 缺少 libfoo.so.1 -> libfoo.so.1.0 的符号链接
```

修复：重新安装库或手工补符号链接，优先让包管理器处理。

### 4. 架构不匹配

```text
wrong ELF class: ELFCLASS32
```

32 位程序加载了 64 位库，或反之。用 `file` 检查程序和库的位数，安装对应架构的库。

### 5. 间接依赖缺失

`app` 依赖 `libA`，`libA` 依赖 `libB`，但 `libB` 没装。`ldd app` 会显示：

```text
libB.so.2 => not found
```

修复：安装 `libB`，或把 `libB` 一起分发并配置 RUNPATH。注意 RUNPATH 不作用于间接依赖，必要时用 RPATH 或在可执行文件上设置 RUNPATH。

### 6. LD_LIBRARY_PATH 不生效

- `sudo` 或 setuid 程序会忽略 `LD_LIBRARY_PATH`（secure-execution 模式）；
- 以 systemd 服务运行时，环境变量需要在 unit 里显式配置；
- 在容器里构建、宿主机运行，路径不一致。

### 7. Windows 缺少 DLL

- 把依赖 DLL 放到 exe 同目录（最稳）；
- 安装 VC++ Redistributable；
- 用 `dumpbin /dependents app.exe` 查看依赖；
- 用 Dependency Walker 或 `Dependencies.exe` 排查。

## 五、排查流程（命令化）

### Step 1：看程序依赖什么

```bash
readelf -d ./app | grep -E 'NEEDED|RPATH|RUNPATH'
objdump -p ./app | grep -E 'NEEDED|RPATH|RUNPATH'
```

### Step 2：看运行时实际找到没有

```bash
ldd ./app                 # 列出解析结果，not found 即缺失
ldd -r ./app              # 同时检查未解析符号
```

### Step 3：看库的 SONAME 和依赖

```bash
objdump -p libfoo.so.1.0 | grep SONAME
ldd libfoo.so.1.0
```

### Step 4：跟踪加载过程

```bash
LD_DEBUG=libs ./app 2>&1 | grep -i foo
strace -f -e trace=openat ./app 2>&1 | grep libfoo
```

### Step 5：确认架构与版本

```bash
file ./app libfoo.so
readelf -h ./app | grep Class
```

## 六、命令速查表

| 目的 | 命令 |
|---|---|
| 查看依赖 | `readelf -d app | grep NEEDED` |
| 查看搜索路径 | `readelf -d app | grep -E 'RPATH\|RUNPATH'` |
| 查看解析结果 | `ldd app` |
| 检查未解析符号 | `ldd -r app` |
| 查看 SONAME | `objdump -p libfoo.so | grep SONAME` |
| 跟踪库加载 | `LD_DEBUG=libs ./app` |
| 修改 RPATH | `patchelf --set-rpath '$ORIGIN/lib' app` |
| 刷新缓存 | `sudo ldconfig` |
| Windows 依赖 | `dumpbin /dependents app.exe` |

## 七、预防规范

1. 发布程序时优先使用 `$ORIGIN` 相对 RUNPATH，把依赖库随包分发。
2. 构建环境与运行环境保持一致（容器化构建/运行最稳）。
3. 不要把 `LD_LIBRARY_PATH` 当作正式部署方案。
4. 库升级时保持 SONAME 兼容；不兼容就提升 SONAME 主版本号。
5. 发布前在干净的目标系统上跑一遍 `ldd app`，确认没有 `not found`。
6. Windows 把运行库或 DLL 放在 exe 同目录，避免依赖开发机 PATH。

## 八、面试标准简答

### 1. 动态链接器怎么找库？

按 DT_RPATH、LD_LIBRARY_PATH、DT_RUNPATH、ld.so.cache、默认系统目录的顺序查找。RUNPATH 与 RPATH 的主要区别是：RPATH 优先于环境变量，RUNPATH 在其后，且 RUNPATH 不传递给间接依赖。

### 2. 为什么编译成功运行却找不到库？

链接期只检查库存在并记录 SONAME，不把库路径和代码复制进程序；运行期由动态链接器重新按搜索路径查找。路径、SONAME、架构、版本任一不匹配都会导致加载失败。

### 3. ldd 的原理和风险？

`ldd` 通过设置 `LD_TRACE_LOADED_OBJECTS=1` 运行目标程序，让动态链接器只打印依赖而不真正执行。对不可信程序使用 ldd 有安全风险，可以用 `objdump -p` 或 `readelf -d` 代替。

### 4. 如何让程序在任何机器上找到自带的 .so？

链接时设置 `-Wl,-rpath,'$ORIGIN/../lib'`，运行时以可执行文件位置为基准查找；同时保证 SONAME 符号链接齐全。比起 `LD_LIBRARY_PATH`，这种方式可随包分发、无需环境变量。
