# 内联函数链接缺失问题

## 一、前言

`inline` 经常被误解为"编译器一定会把函数展开"。实际上：

- `inline` 只是**建议**，编译器可以选择不展开；
- 不展开时，编译器必须生成一份**外联（out-of-line）定义**；
- 这份定义必须在链接时找得到，否则就是 `undefined reference`。

核心总纲：**inline 允许重复定义，但前提是每个使用它的编译单元都能看到定义。** 只声明、不定义，链接器就找不到。

## 二、底层机制

### 1. inline 函数在目标文件中的形态

- 编译器内联展开时，函数体直接嵌入调用点，不产生独立符号；
- 不内联时（`-O0`、取函数地址、函数体太大、递归、虚调用等），生成一份**弱符号（W）** 的 out-of-line 副本；
- 多个编译单元各自生成一份弱符号，链接器按 COMDAT 规则合并成一份。

所以，只要定义在每个使用它的编译单元可见，链接就没问题——重复定义由弱符号机制消化。

### 2. 只有声明、没有定义会怎样

```cpp
// foo.h
inline void foo();

// foo.cpp
void foo() { }        // 定义只在这一个编译单元

// main.cpp
foo();                // 只看到声明，无法内联也没有定义 → U 符号 → undefined reference
```

`main.cpp` 生成对 `foo` 的未定义引用，链接器在 `foo.cpp` 的目标文件里其实有定义——但 `foo.cpp` 没被指定 `inline`？关键问题不是有没有 `inline`，而是**定义是否在 `main.cpp` 可见**。`main.cpp` 看不到函数体，编译器只能留下外部引用；如果 `foo.cpp` 里的定义因为 `inline` 语义没有生成强符号，链接器就找不到。

### 3. C 与 C++ 的 inline 语义差异

C++：

- `inline` 函数允许在多个编译单元定义（必须完全相同）；
- 定义放头文件是标准做法。

C99：

- 头文件里的 `inline` 定义只提供"内联定义"，**不保证生成外部定义**；
- 如果没有某个编译单元提供 `extern inline` 外部定义，未内联的调用可能找不到符号；
- `static inline` 每个编译单元各自生成内部链接副本，最稳妥但会增大代码体积。

GNU89 与 C99 的 `inline` / `extern inline` 语义正好相反，混用工具链时极易踩坑。**头文件里推荐 `static inline`（C）或 `inline`（C++）。**

### 4. 类的成员函数

- 在类体内定义：隐式 `inline`，放头文件没问题；
- 在类体外、头文件中定义：必须显式写 `inline`，否则多个编译单元包含时出现 `multiple definition`；
- 在 `.cpp` 中定义：正常的外部函数，不存在内联链接问题，但也无法跨编译单元内联。

### 5. 取地址与虚函数

一旦对 inline 函数取地址，或通过函数指针调用，编译器必须生成 out-of-line 副本。只要定义可见，仍然没问题；定义不可见就会出现未定义引用。

## 三、高频场景

### 1. 头文件声明 inline，源文件定义

```cpp
// foo.h
inline void foo();

// foo.cpp
inline void foo() { }    // 定义仅此一处

// main.cpp
foo();                   // undefined reference to `foo()'
```

修复：把定义移到头文件；或去掉 `inline` 并在头文件只留声明、`.cpp` 提供普通定义。

### 2. 类成员函数在 .cpp 定义但未导出

```cpp
// widget.h
class Widget {
public:
    void draw();         // 只是声明
};

// widget.cpp
void Widget::draw() { }  // 正常外部定义

// main.cpp 调用 Widget::draw() —— 只要 widget.cpp 参与链接就没问题
```

这种写法本身没问题。真正的问题是 `widget.cpp` 漏加进构建，或库没有导出该符号。

### 3. C 头文件里使用裸 `inline`

```c
// util.h
inline int max(int a, int b) { return a > b ? a : b; }
```

在 C99 下，多个编译单元包含后，可能没有任何外部定义；未内联的调用会报 `undefined reference to 'max'`。修复：

```c
static inline int max(int a, int b) { return a > b ? a : b; }   // 推荐
```

### 4. 调试构建下突然报错

`-O0` 下编译器更少内联，更多函数需要 out-of-line 副本。如果定义不可见，Release（`-O2`）可能碰巧全内联通过，Debug 却链接失败。**不要用"Release 能过"判断代码正确。**

### 5. 动态库导出 inline 函数

inline 函数默认是弱符号，且可能被隐藏（`-fvisibility=hidden`）。如果其他库需要调用它，要么确保定义在头文件里（各自实例化），要么显式导出并关闭内联。

## 四、排查流程

### Step 1：看符号是 U 还是 W

```bash
nm -C main.o | grep ' foo'
# U foo()  -> 未定义引用
# W foo()  -> 有弱定义（out-of-line 副本）
```

### Step 2：确认定义在哪个编译单元

```bash
nm -C -A *.o | grep ' foo'
```

### Step 3：看预处理后的头文件

```bash
g++ -E main.cpp | grep -A3 'foo'
```

### Step 4：跟踪链接解析

```bash
g++ main.o foo.o -Wl,--trace-symbol=_Z3foov -o app
```

### Step 5：确认编译选项

```bash
g++ -### -c main.cpp 2>&1 | grep -E 'O[0-9]|fno-inline'
```

## 五、修复方案速查

| 场景 | 修复 |
|---|---|
| inline 函数定义在 `.cpp` | 定义移到头文件 |
| 头文件只有声明 | 补定义到头文件，或去掉 inline 改为普通函数 |
| C 头文件裸 `inline` | 改为 `static inline`，或统一用 `extern inline` 方案 |
| 类外成员函数在头文件 | 加 `inline` |
| 定义在 `.cpp` 但漏编译 | 把源文件加入构建 |
| 需要跨库调用 | 头文件提供定义，或显式导出非 inline 版本 |
| Debug 构建失败 | 检查定义可见性，不要依赖编译器内联 |

## 六、预防规范

1. C++ 的 inline 函数定义放头文件；类外定义在头文件时必须写 `inline`。
2. C 头文件统一用 `static inline`，避免 C99/GNU89 语义差异。
3. 不要用"Release 能链接"证明代码正确，Debug 构建要一起验证。
4. 公共库的 API 如果需要在多个库间共享，不要依赖 inline 弱符号，提供明确的导出函数。
5. 对性能关键的小函数用 inline；大函数交给编译器决定，不要强求。
6. 开启 `-Wall -Wextra`，关注 `inline function used but never defined` 警告。

## 七、面试标准简答

### 1. inline 函数为什么会出现 undefined reference？

`inline` 只是建议，编译器可能生成 out-of-line 副本。生成副本需要函数定义，而其他编译单元只看到了声明，定义不可见时只能留下未定义引用，链接器就报错。解决方法是把定义放到头文件。

### 2. inline 函数为什么允许多个编译单元重复定义？

标准规定 inline 函数可以有多个相同定义，编译器为每个副本生成弱符号（COMDAT），链接器负责合并成一份。前提是所有定义完全一致，否则属于 ODR 违规。

### 3. static inline 和 inline 的区别？

`static inline` 是内部链接，每个编译单元各自生成一份副本，不参与全局符号解析，因此不会有链接冲突，但会增加代码体积；普通 `inline` 是外部链接的弱符号，多个副本由链接器合并。

### 4. C 语言的 inline 有什么坑？

C99 的裸 `inline` 定义不保证生成外部定义，未内联的调用可能找不到符号；GNU89 与 C99 的 `inline`/`extern inline` 语义相反。头文件里使用 `static inline` 最稳妥。
