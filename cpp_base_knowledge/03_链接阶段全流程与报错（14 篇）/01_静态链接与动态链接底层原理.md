# 静态链接与动态链接底层原理

## 一、前言

链接是把多个目标文件（`.o`）组装成可执行文件或共享库的过程。按符号解析和代码组织的时机，分为两种：

- **静态链接**：链接期把所有需要的代码复制进最终产物，产物自包含；
- **动态链接**：链接期只记录"我依赖谁"，真正的符号解析和地址绑定推迟到加载/运行时。

核心总纲：**静态是复制，动态是引用。** 静态换部署简单，动态换内存共享、可升级和体积。

## 二、静态链接

### 1. 静态库的本质

`.a` 不是"一个库文件"，而是**一组 `.o` 的归档包**（ar archive）：

```bash
ar t libfoo.a          # 列出成员 .o
ar x libfoo.a          # 解包
ar rcs libfoo.a a.o b.o
```

链接器面对 `.a` 时不是全部搬走，而是按需抽取：只有当某个成员能定义**当前未定义符号**时，才把该成员加入链接。

### 2. 链接过程

1. 链接器从左到右扫描命令行上的 `.o` 和 `.a`；
2. 维护一个"未定义符号集合"；
3. 遇到 `.o` 直接加入；遇到 `.a` 则检查成员是否定义当前未解析符号，命中就抽取该成员，并把它新引入的未定义符号加入集合；
4. 全部扫描完后仍有未定义符号 → `undefined reference`；
5. 分配地址、完成重定位，符号地址在链接期就固定。

### 3. 特点

| 优点 | 缺点 |
|---|---|
| 运行时无额外依赖，部署简单 | 可执行文件体积大 |
| 启动不需要加载库、解析符号 | 库升级必须重新链接 |
| 不怕目标机器缺少 `.so` | 多个进程无法共享代码页 |
| 排查简单，符号都在产物里 | 多个静态库可能符号冲突 |

### 4. 常用命令

```bash
gcc main.o -lfoo -static -o app          # 尽量全静态
gcc main.o -Wl,-Bstatic -lfoo -Wl,-Bdynamic -lbar -o app  # 指定某个库静态链接
file app                                  # 看是否 "statically linked"
ldd app                                   # 静态程序会提示 not a dynamic executable
```

## 三、动态链接

### 1. 共享库的本质

`.so`（Windows 为 `.dll`）是 **ELF `ET_DYN`** 类型的共享对象，通常要求位置无关代码：

```bash
gcc -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.0 foo.c
ln -s libfoo.so.1.0 libfoo.so.1
ln -s libfoo.so.1.0 libfoo.so        # 链接期用的名字
```

三个名字各有用处：

- `libfoo.so`：**链接名**，`-lfoo` 找它，通常只是符号链接；
- `libfoo.so.1`：**SONAME**，运行时记录在 `DT_NEEDED` 里的名字；
- `libfoo.so.1.0`：**真实文件**。

### 2. 链接期发生了什么

链接器**不复制库代码**，只做三件事：

1. 检查依赖库中是否存在所需符号（`-l` 能找到即可，具体地址不管）；
2. 在可执行文件里写入 `DT_NEEDED` 条目，记录依赖的 SONAME；
3. 为动态符号调用生成 PLT/GOT 跳板，地址留到加载时填。

所以链接成功不代表运行一定能跑——运行时找库、找符号是另一套机制。

### 3. 加载期发生了什么

程序启动时，内核发现 ELF 的 `PT_INTERP`，先加载动态链接器 `ld-linux-x86-64.so.2`，由它：

1. 按搜索顺序找到所有 `DT_NEEDED` 库并映射进地址空间；
2. 建立全局符号表，按广度优先顺序解析符号（可执行文件优先，其次依赖顺序）；
3. 完成数据重定位；函数符号默认**惰性绑定**，第一次调用时经 PLT 解析；
4. 执行各库的 `DT_INIT_ARRAY` 构造器；
5. 跳转到程序入口 `_start`，最终进入 `main`。

### 4. 内存共享

- `.text`、`.rodata` 等只读页在多个进程间**物理共享**；
- `.data`、`.bss` 每个进程一份，写时复制（COW）；
- 这是动态链接省内存的根本原因。

### 5. 特点

| 优点 | 缺点 |
|---|---|
| 多进程共享代码页，省内存 | 运行时依赖库和搜索路径 |
| 库升级不需要重编主程序（保持 ABI 兼容） | 可能出现版本/符号不兼容 |
| 产物体积小 | 启动要做符号解析和重定位 |
| 插件化、`dlopen` 动态加载 | 排查链路更长 |

## 四、关键机制对比

| 维度 | 静态链接 | 动态链接 |
|---|---|---|
| 链接期 | 复制代码、完成重定位 | 只记录依赖、生成 PLT/GOT |
| 符号地址确定时间 | 链接期 | 加载期 / 首次调用（惰性） |
| 运行时依赖 | 无 | `.so` / `.dll` |
| 体积 | 大 | 小 |
| 内存共享 | 不能 | 只读页可共享 |
| 升级库 | 需重新链接 | 替换 `.so`，但 ABI 必须兼容 |
| 常见故障 | 符号重复、库顺序 | 找不到库、找不到符号、版本不兼容 |
| 典型命令 | `-static` | `-fPIC -shared` |

## 五、PIC、PLT 与 GOT

- **PIC（位置无关代码）**：代码不写死加载地址，使用 RIP 相对寻址和 GOT 间接寻址。共享库必须 `-fPIC`，否则会出现 `text relocations`，且无法在多个进程间安全共享。
- **GOT（全局偏移表）**：存放外部符号的实际地址，加载时由动态链接器填写。
- **PLT（过程链接表）**：每个外部函数一个跳板，第一次调用触发动态解析，之后 GOT 缓存地址，直接跳转。

```bash
readelf -r app          # 查看重定位项
objdump -d app | grep '@plt'   # 查看 PLT 调用
```

## 六、常见问题

### 1. 全静态链接 glibc

`-static` 链接 glibc 会带来 NSS、`getaddrinfo`、`dlopen` 等一系列运行时警告/失败，因为 glibc 大量功能依赖动态加载。工程上更常见的做法是：**只静态链接 C++ 运行库**，glibc 保持动态。

```bash
g++ main.cpp -static-libstdc++ -static-libgcc -o app
```

### 2. 静态与动态混用

`-Wl,-Bstatic -lfoo -Wl,-Bdynamic` 只影响其后出现的库，顺序写错会得到意料之外的结果。链接命令里混用两套 libstdc++ 还可能导致 ABI 冲突或重复符号。

### 3. ldd 的局限

`ldd` 本质上是以 `LD_TRACE_LOADED_OBJECTS=1` 运行程序，只列直接/间接依赖，不保证符号能解析。要检查未解析符号用：

```bash
ldd -r ./app
```

### 4. 部署时找不到库

静态链接可以通过"全静态"规避；动态链接需要处理 RPATH/RUNPATH 或 `LD_LIBRARY_PATH`，详见后续《动态库.so/.dll 依赖缺失报错》。

## 七、命令速查表

| 目的 | 命令 |
|---|---|
| 查看是否静态 | `file app` |
| 查看动态依赖 | `ldd app` / `readelf -d app | grep NEEDED` |
| 查看 SONAME | `objdump -p libfoo.so | grep SONAME` |
| 查看 RPATH/RUNPATH | `readelf -d app | grep -E 'RPATH\|RUNPATH'` |
| 查看动态符号 | `objdump -T libfoo.so` |
| 查看重定位 | `readelf -r app` |
| 解包静态库 | `ar x libfoo.a` |
| 全静态链接 | `gcc ... -static` |
| 只静态 C++ 运行库 | `g++ ... -static-libstdc++ -static-libgcc` |

## 八、面试标准简答

### 1. 静态链接和动态链接的区别？

静态链接在链接期把库代码复制进可执行文件，符号地址固定，产物自包含；动态链接只记录依赖的 SONAME，运行时由动态链接器加载 `.so` 并完成符号解析和重定位，多个进程可共享只读代码页。

### 2. 为什么共享库要加 -fPIC？

共享库的加载地址在编译期未知，且同一份代码要能被多个进程映射到不同地址。PIC 使用 RIP 相对寻址和 GOT，避免绝对地址重定位；不加 `-fPIC` 会产生文本重定位，链接器通常直接报错。

### 3. 全静态链接有什么坑？

glibc 的 NSS（用户名/域名解析）、`dlopen`、locale 等功能依赖动态加载机制，全静态链接后可能运行失败；此外静态产物体积大、无法共享内存、安全更新需要重新编译发布。

### 4. 什么时候优先静态链接？

工具类小程序、容器镜像需要自包含、目标环境库版本不可控、对启动速度敏感的场景。大型服务通常选动态链接，便于统一升级和共享内存。

## 九、极简口诀

**静态复制进产物，动态只记依赖名；**

**链接成功不代表能跑，加载还要找符号；**

**共享库要 -fPIC，PLT/GOT 填地址；**

**全静态避开 glibc，C++ 库可单独静。**
