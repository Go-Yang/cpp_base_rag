# 程序崩溃、段错误通用定位链路

## 一、前言

"程序挂了"可能是很多原因：段错误、断言、堆损坏、OOM、未捕获异常。定位的关键不是背命令，而是**按层缩小范围**：

1. 进程怎么死的（信号/退出码）？
2. 死在哪条指令（崩溃现场）？
3. 为什么访问非法（地址、权限、生命周期）？
4. 谁把它带到这里的（调用栈、输入、时序）？

核心总纲：**先拿现场，再做假设，用实验验证。** 不要凭感觉改代码。

## 二、第一步：确认死亡方式

### 1. 退出码与信号

```bash
./app; echo $?
```

- `139` = 128 + 11 = SIGSEGV；
- `134` = 128 + 6 = SIGABRT；
- `135` = 128 + 7 = SIGBUS；
- `137` = 128 + 9 = SIGKILL（常见于 OOM Killer）；
- `136` = 128 + 8 = SIGFPE。

### 2. 内核日志

```bash
dmesg -T | tail -50
journalctl -k --since "10 min ago"
```

能看到段错误地址、OOM Killer 记录。

### 3. systemd-coredump

```bash
coredumpctl list
coredumpctl info <pid>
coredumpctl debug <pid>
```

## 三、第二步：拿崩溃现场

### 1. CoreDump

```bash
ulimit -c unlimited
./app
gdb ./app core
```

详见《CoreDump 开关配置与崩溃文件生成》《CoreDump 堆栈解析完整排错流程》。

### 2. 没有 core 时

- `dmesg` 里的 `segfault at <addr> ip <pc> sp <sp> error <code>`；
- 重新在开发环境开启 core/ASAN 复现；
- 加日志缩小范围；
- 用 `strace` 看最后几个系统调用。

### 3. ASAN 复现

```bash
gcc -fsanitize=address -fno-omit-frame-pointer -g app.c -o app
./app
```

对内存类崩溃，ASAN 的报告比 core 更直接。

## 四、第三步：分类根因

| 现象 | 可能原因 | 首选工具 |
|---|---|---|
| `si_addr = 0x0` | 空指针解引用 | gdb + 源码 |
| 地址随机、非映射 | 野指针/悬空指针 | ASAN |
| 写只读页 | 改字符串字面量/常量/代码 | gdb `info proc mappings` |
| 栈顶接近 guard | 栈溢出/深递归 | gdb `bt`、`ulimit -s` |
| 崩溃在 malloc/free | 堆损坏、double free | ASAN/Valgrind |
| `__stack_chk_fail` | 栈缓冲区溢出 | gdb + 源码 |
| SIGBUS | 未对齐访问/映射文件截断 | gdb `si_addr`、`file` |
| SIGKILL + dmesg OOM | 内存超限 | dmesg、cgroup 统计 |
| SIGABRT + assert | 断言失败/主动 abort | gdb `bt`、日志 |

## 五、第四步：定位代码

1. `bt` 找调用链；
2. `frame N` + `info locals/args` 看变量；
3. `x/i $pc` 和反汇编确认指令；
4. `addr2line`/`list` 定位源码；
5. 检查输入、边界、生命周期、并发。

### 1. 空指针

- 返回值未判空；
- 成员指针未初始化；
- 回调参数为 NULL；
- 对象已释放但指针未置空。

### 2. 悬空指针

- free/delete 后继续使用；
- 容器扩容后旧指针失效；
- 返回局部变量地址；
- 多所有者重复释放。

### 3. 栈溢出

- 深递归；
- 大局部数组；
- 线程栈太小；
- 无限递归。

### 4. 堆损坏

- 越界写破坏 chunk 元数据；
- double free；
- 释放非堆指针；
- 多线程无锁访问同一分配器结构。

## 六、第五步：验证与回归

1. 用最小输入复现；
2. ASAN/Valgrind 验证修复；
3. 加单元测试/回归用例；
4. 压测/长时间运行观察；
5. 必要时加断言和日志，防止复发。

## 七、常见"看不见的崩溃"

### 1. OOM Killer

进程被 SIGKILL，没有 core。查：

```bash
dmesg -T | grep -i 'killed process'
cat /sys/fs/cgroup/memory.max
```

### 2. 未捕获 C++ 异常

`std::terminate` → `abort`。看 `bt` 里的 `__cxa_throw` / `terminate`。

### 3. 栈溢出破坏栈

`bt` 可能失败。用 `x/64gx $rsp` 手动扫描，或 ASAN 的 stack-overflow 报告。

### 4. 信号处理函数出错

信号处理里调用非 async-signal-safe 函数（printf、malloc）可能死锁/崩溃。用 `write` 或设置标志位。

### 5. 动态库版本不匹配

崩溃在库内部，栈符号对不上。检查 `ldd`、build-id、ABI。

## 八、标准定位链路（ checklist）

1. 退出码/信号 → 2. dmesg/journal → 3. core 或 ASAN → 4. `bt` → 5. 故障地址与映射 → 6. 反汇编/源码 → 7. 变量与输入 → 8. 最小复现 → 9. 修复 → 10. 回归。

## 九、面试标准简答

### 1. 段错误怎么定位？

先确认信号和故障地址，用 core/gdb 看崩溃指令和调用栈，对照 `/proc/pid/maps` 判断地址权限，再结合源码、ASAN/Valgrind 和最小复现定位根因。

### 2. 为什么程序崩溃但没有 core？

`ulimit -c 0`、core_pattern 不可写、进程不可 dump、容器限制、磁盘满、SIGKILL 不产生 core。逐项检查。

### 3. OOM 和段错误怎么区分？

OOM 通常表现为 SIGKILL（退出码 137），dmesg 有 "Killed process"，没有 core；段错误是 SIGSEGV（139），可能有 core，故障地址非法。

### 4. 崩溃在 malloc/free 内部说明什么？

大概率是堆元数据被越界写破坏、double free 或非法 free，而不是分配器本身有 bug。用 ASAN/Valgrind 复现，找第一次破坏堆的地方。

## 十、极简口诀

**先看信号和退出码，dmesg 找 OOM；**

**有 core 看栈，无 core 开 ASAN；**

**空指针小偏移，随机地址查悬空；**

**堆坏在 malloc，栈坏在 canary。**
