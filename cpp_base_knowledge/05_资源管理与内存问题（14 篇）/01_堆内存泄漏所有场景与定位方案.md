# 堆内存泄漏所有场景与定位方案

## 一、前言

内存泄漏是指**程序分配了堆内存，但在丢失所有引用之前没有释放**。泄漏的后果：

- 进程 RSS 持续上涨，最终 OOM；
- 分配器碎片化，分配变慢；
- 长周期服务（网关、数据库、游戏服务器）中尤其致命。

核心总纲：**泄漏 = 分配了 + 没人负责释放 + 指针丢失。** 定位的关键不是看哪里申请得多，而是看"谁申请、谁释放、所有权在谁手里"。

## 二、泄漏的分类（Valgrind 口径）

| 类型 | 含义 |
|---|---|
| definitely lost | 确定泄漏：没有任何指针指向该块 |
| indirectly lost | 间接泄漏：父块泄漏导致子块也丢了 |
| possibly lost | 可能泄漏：指针指向块内部而不是头部 |
| still reachable | 仍可达：全局/静态/栈上还有指针，程序退出前没释放 |

`still reachable` 不一定是 bug（很多库故意缓存到进程退出），但在长周期服务里同样会积累。

## 三、常见泄漏场景

### 1. 路径遗漏

```c
char* buf = malloc(n);
if (error) {
    return -1;        // 漏了 free(buf)
}
free(buf);
```

每个 early return、每个错误分支都要检查释放。C++ 用 RAII 可彻底规避。

### 2. 指针被覆盖

```c
p = malloc(100);
p = malloc(200);      // 第一块永远泄漏
```

### 3. 容器存指针

```cpp
std::vector<Foo*> v;
v.push_back(new Foo);
v.clear();            // 只销毁指针，不 delete 对象
```

改用 `std::vector<std::unique_ptr<Foo>>`。

### 4. 缺少虚析构函数

```cpp
struct Base { ~Base() {} };          // 非 virtual
struct Derived : Base { char* data; };
Base* p = new Derived;
delete p;                            // 只调用 Base 析构，Derived::data 泄漏
```

基类析构必须 `virtual`。

### 5. new[] / delete 不匹配

```cpp
int* a = new int[10];
delete a;             // UB，通常泄漏或崩溃
```

必须 `delete[] a`；更推荐 `std::vector`。

### 6. shared_ptr 循环引用

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;   // 两个 shared_ptr 互相引用，计数永不归零
};
```

用 `weak_ptr` 打断循环。

### 7. 全局/静态容器只增不减

```cpp
static std::map<int, Data*> cache;   // 只插入不清理，等同于泄漏
```

需要容量上限、TTL、LRU 淘汰。

### 8. 线程退出未清理

线程申请的堆内存，如果没有归属到某个对象，线程结束时不会自动释放。

### 9. 第三方 API 返回所有权

`strdup`、`getline`、`realpath`、`asprintf` 等会分配内存，需要调用者 `free`。C API 文档里的"caller owns"必须当回事。

### 10. 回调/事件未注销

注册了监听器，对象销毁时没注销，回调持有对象指针，导致对象无法释放。

### 11. 异常路径

```cpp
Foo* p = new Foo;
may_throw();          // 抛异常，p 泄漏
delete p;
```

用智能指针或 `try/catch` 清理。

## 四、定位方案

### 1. Valgrind

```bash
valgrind --leak-check=full --show-leak-kinds=all \
         --track-origins=yes --error-exitcode=1 ./app
```

输出会给出泄漏块的分配调用栈，直接定位到 `malloc/new` 的源码行。

### 2. ASAN / LeakSanitizer

```bash
gcc -fsanitize=address -fno-omit-frame-pointer -g app.c -o app
ASAN_OPTIONS=detect_leaks=1 ./app
```

程序退出时打印泄漏报告，含分配栈。适合开发和 CI。

### 3. heaptrack / massif

```bash
heaptrack ./app
valgrind --tool=massif ./app
massif-visualizer massif.out.*
```

看内存随时间增长的趋势和热点分配点，适合"缓慢泄漏"。

### 4. 运行时统计

```c
malloc_stats();
struct mallinfo2 mi = mallinfo2();   // uordblks 等
```

定时打印，观察是否单调增长。

### 5. /proc 观察

```bash
grep -E 'VmRSS|VmSize' /proc/<pid>/status
cat /proc/<pid>/smaps | grep -A10 heap
```

RSS 持续上涨是泄漏的典型信号，但要先排除分配器缓存和碎片。

## 五、修复与预防

1. **RAII 优先**：C++ 用 `std::unique_ptr`、`std::vector`、`std::string`；C 用统一的 cleanup 标签。
2. **所有权明确**：函数文档写明"caller owns"还是"callee owns"。
3. **基类虚析构**。
4. **容器存对象或智能指针**，不存裸指针。
5. **打破 shared_ptr 循环**：用 `weak_ptr`。
6. **缓存要有上限**：LRU、TTL、定时清理。
7. **异常安全**：用智能指针保证异常路径也释放。
8. **CI 中跑 ASAN/LSan**，把泄漏挡在合并前。

## 六、排查流程

1. 复现：能否稳定增长？压测/长时间运行；
2. 观察：RSS、`malloc_stats`、`/proc/smaps`；
3. 抓取：ASAN 或 Valgrind 跑代表性场景；
4. 归因：看分配调用栈，确认所有权；
5. 修复：RAII/所有权调整；
6. 回归：CI 跑 ASAN/LSan，观察 RSS 曲线。

## 七、面试标准简答

### 1. 什么是内存泄漏？

程序分配了堆内存，在失去所有指向它的引用之前没有释放，导致该内存无法再被使用。长周期进程会因此持续增长直至 OOM。

### 2. Valgrind 的 definitely lost 和 still reachable 有什么区别？

`definitely lost` 是没有任何指针能到达的块，确定泄漏；`still reachable` 是退出时仍有全局/栈指针指向的块，可能是有意缓存，但在长周期服务里也可能是问题。

### 3. 如何避免 C++ 内存泄漏？

用 RAII 和智能指针管理所有权；容器存对象而非裸指针；基类虚析构；shared_ptr 循环用 weak_ptr；异常路径也用智能指针；CI 跑 ASAN/Valgrind。

### 4. 为什么 shared_ptr 会循环引用泄漏？

两个对象互相持有 `shared_ptr`，引用计数永远不归零，析构永远不触发。把其中一边改成 `weak_ptr` 即可打破循环。

## 八、极简口诀

**泄漏三要素：申请、丢指针、没释放；**

**错误分支要清理，容器别存裸指针；**

**基类虚析构，循环用 weak；**

**Valgrind 看栈，ASAN 进 CI。**
