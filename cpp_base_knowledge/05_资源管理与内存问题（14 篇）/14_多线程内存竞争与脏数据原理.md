# 多线程内存竞争与脏数据原理

## 一、前言

多个线程访问同一块内存，至少一个写，且没有同步，就叫**数据竞争（data race）**。在 C++ 内存模型里，数据竞争是**未定义行为**——不是"结果可能旧"，而是编译器可以假设它不存在，做出任意优化。

核心总纲：**没有 happens-before 的并发读写，结果不可预测。** 脏数据、丢更新、崩溃都只是表象，根因是缺少同步或同步方式错误。

## 二、典型竞争场景

### 1. 计数器丢更新

```cpp
int counter = 0;
// 两个线程各执行 100 万次
counter++;   // 读-改-写不是原子操作
```

两个线程可能同时读到同一个旧值，各自加一写回，结果小于 200 万。

### 2. 标志位可见性

```cpp
bool ready = false;
// 线程 A
data = 42; ready = true;
// 线程 B
while (!ready) {}
use(data);    // 可能看到 ready=true 但 data 还是旧值
```

编译器和 CPU 都可能重排，`ready` 置位的顺序不保证。需要原子变量 + acquire/release 或互斥锁。

### 3. 64 位读写撕裂（32 位平台）

32 位平台上，64 位变量的读写在硬件层可能分成两次 32 位操作，另一个线程可能读到"半新半旧"的值（torn read）。

### 4. 双重检查锁定

```cpp
if (!instance) {
    std::lock_guard<std::mutex> lock(m);
    if (!instance) instance = new Foo;
}
return instance;   // 第一次检查无同步，可能看到未构造完成的对象
```

C++11 起应使用函数内 static，或用 `std::atomic` + acquire/release。

### 5. 容器并发修改

一个线程 `push_back`，另一个线程遍历，迭代器/内部指针失效，崩溃或脏数据。

### 6. 对象半初始化发布

线程 A 构造对象后把指针写到共享变量，线程 B 通过共享变量读取。若没有同步，B 可能看到指针但对象构造尚未完成。

## 三、底层原因

### 1. 编译器重排

编译器可以在不改变单线程语义的前提下重排指令。没有同步点时，它不知道其他线程的存在。

### 2. CPU 重排与缓存

- 每个核有自己的缓存和 store buffer；
- 写操作可能延迟对其他核可见；
- 缓存一致性协议（MESI）保证最终一致，但不保证顺序；
- `volatile` 不提供跨线程同步语义（它只约束编译器对该对象的访问）。

### 3. 内存模型

C++11 定义了 happens-before 关系：

- 同一线程内的语句按程序顺序；
- 互斥锁 unlock 与后续 lock 建立同步；
- 原子操作的 release/acquire 建立同步；
- 线程 start/join 建立同步。

只有建立了 happens-before，一个线程的写才能被另一个线程安全看到。

## 四、同步机制

### 1. 互斥锁

```cpp
std::mutex m;
{
    std::lock_guard<std::lock_guard> lock(m);
    counter++;
}
```

- 保护临界区；
- `std::lock_guard`/`std::unique_lock` RAII；
- 多锁用 `std::scoped_lock` 避免死锁；
- 锁粒度要合理，避免持锁做 IO。

### 2. 原子变量

```cpp
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);
```

内存序：

| 内存序 | 含义 |
|---|---|
| `relaxed` | 只保证原子性，不保证顺序 |
| `acquire` | 读之后的访问不能重排到它前面 |
| `release` | 写之前的访问不能重排到它后面 |
| `acq_rel` | 读写双向 |
| `seq_cst` | 全局顺序一致（默认，最严格） |

标志位典型写法：

```cpp
std::atomic<bool> ready{false};
// A
data = 42;
ready.store(true, std::memory_order_release);
// B
while (!ready.load(std::memory_order_acquire)) {}
use(data);
```

### 3. 条件变量

```cpp
std::mutex m;
std::condition_variable cv;
bool ready = false;

// 等待方
std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [&]{ return ready; });

// 通知方
{
    std::lock_guard<std::mutex> lock(m);
    ready = true;
}
cv.notify_one();
```

条件变量必须配合互斥锁，并处理虚假唤醒（用谓词）。

### 4. thread_local

每个线程一份数据，天生无竞争；适合缓存、错误码、随机数状态。注意生命周期和内存增长。

### 5. 不可变数据

`const`/只读数据无需同步，是最简单的并发安全方式。

## 五、伪共享

两个线程写同一缓存行中的不同变量，缓存行在核间反复失效，性能大幅下降：

```cpp
struct Counters {
    alignas(64) std::atomic<long> a;
    alignas(64) std::atomic<long> b;
};
```

这不是正确性问题，但会让"加了锁/原子"的程序依然很慢。

## 六、检测工具

### 1. ThreadSanitizer（TSan）

```bash
gcc -fsanitize=thread -g app.c -o app
./app
```

能报 data race，给出两个访问的调用栈。开销较大，适合测试。

### 2. Valgrind Helgrind / DRD

```bash
valgrind --tool=helgrind ./app
valgrind --tool=drd ./app
```

检测锁顺序、数据竞争，速度慢。

### 3. 代码审查

- 找出所有共享可变状态；
- 检查每个访问是否有同步；
- 检查锁是否覆盖所有路径；
- 检查原子操作的内存序是否足够。

## 七、修复与预防

1. 尽量减少共享可变状态；优先不可变数据。
2. 共享数据用互斥锁保护，锁的粒度与生命周期清晰。
3. 简单标志/计数用原子变量，内存序按需选择，不确定先用 `seq_cst`。
4. 不要用 `volatile` 做线程同步。
5. 容器并发访问要加锁，或使用并发容器。
6. 对象发布用同步机制，避免半初始化。
7. 用 TSan/Helgrind 做并发测试，压测多跑几轮。
8. 避免伪共享，热点变量按缓存行隔离。

## 八、面试标准简答

### 1. 什么是数据竞争？

两个线程并发访问同一内存位置，至少一个是写，且没有同步（没有 happens-before 关系）。在 C++ 中是未定义行为。

### 2. 原子变量和互斥锁怎么选？

单个变量的读改写/标志位用原子变量，开销小；需要保护多个变量或不变量（invariant）时用互斥锁。原子操作不能替代复杂临界区。

### 3. volatile 能保证线程安全吗？

不能。`volatile` 只阻止编译器优化对该对象的访问，不提供原子性、内存屏障或跨线程同步。线程间通信要用 `std::atomic` 或锁。

### 4. 什么是伪共享？

多个线程写同一缓存行中的不同变量，缓存一致性协议导致该行在核间反复失效，性能下降。用 `alignas(64)` 隔离热点变量。

## 九、极简口诀

**共享可写又无锁，数据竞争未定义；**

**锁护临界区，原子保标志；**

**volatile 不同步，内存序分 acquire/release；**

**缓存行六十四，伪共享要隔开。**
