# include守卫与pragma once工程规范

## 一、底层作用本质

头文件守卫是**预处理阶段的防重复拷贝机制**，核心作用：解决同一头文件被多次 include 引发的**类型重定义、变量重定义、代码重复粘贴报错**。

由于 \#include 是纯文本拷贝，工程中一个头文件会被多个源文件、多个头文件嵌套引用，若无守卫，预处理会反复

## 二、传统标准守卫：\#ifndef / \#define / \#endif

### 1\. 标准写法

```c
#ifndef HEADER_TEST_H
#define HEADER_TEST_H

// 头文件全部内容：结构体、类、函数声明、宏、枚举

#endif // HEADER_TEST_H

```

### 2\. 执行逻辑

- 第一次包含：HEADER\_TEST\_H 未定义，进入代码区，执行 define 定义宏

- 第二次及多次包含：宏已存在，直接跳过整个头文件内容

### 3\. 优缺点

**优点**：C/C\+\+ 标准语法、跨平台100%兼容、所有编译器（GCC/Clang/MSVC）通用，无兼容性风险。

**缺点**：需要手动编写、宏命名不规范易出现**宏冲突**（不同头文件使用相同宏名）。

## 三、现代简写守卫：\#pragma once

### 1\. 标准写法

```c
#pragma once

// 头文件全部内容

```

### 2\. 执行逻辑

编译器级指令，自动识别**当前文件物理路径唯一**，只要该文件已被包含过一次，后续全部自动跳过，无需手动定义宏。

### 3\. 优缺点

**优点**：代码简洁、零宏冲突、无需手动维护命名、工程可读性更强。

**缺点**：非C\+\+标准语法（编译器扩展），极老旧编译器、特殊交叉编译环境存在兼容概率问题。

## 四、两种守卫核心差异对比

- **兼容性**：\#ifndef 全平台通用；\#pragma once 主流编译器兼容，老旧环境不保证

- **冲突风险**：\#ifndef 存在宏命名冲突风险；\#pragma once 无冲突

- **维护成本**：\#ifndef 高；\#pragma once 极低

- **识别依据**：\#ifndef 依赖宏名；\#pragma once 依赖文件物理路径

## 五、工程最优规范（通用落地标准）

### 1\. 通用跨平台工程（推荐）

采用**双重守卫**，兼顾兼容性与简洁性，无任何副作用：

```c
#pragma once
#ifndef HEADER_TEST_H
#define HEADER_TEST_H

// 业务代码

#endif

```

### 2\. 嵌入式/老旧交叉编译工程

仅使用 **\#ifndef 传统守卫**，彻底规避编译器扩展兼容问题。

### 3\. 桌面/服务端现代工程

可单独使用 **\#pragma once**，提升开发效率。

## 六、宏冲突问题与规避方案

多个头文件使用相同宏名，会导致**后加载的头文件被静默屏蔽**，出现诡异的未定义类型报错，极难排查。

**宏命名规范**：项目名\_模块名\_文件名\_H，例如：

```c
#ifndef ROBOT_UTILS_LOG_H
#define ROBOT_UTILS_LOG_H

```

## 七、典型报错场景与根因

- **redefinition of struct/class**：无头文件守卫，多次重复包含

- **unresolved reference**：守卫宏冲突，头文件被异常屏蔽

- **incomplete type**：部分场景守卫逻辑导致头文件未完整加载

## 八、最终工程总结

1. 所有自定义头文件**必须添加守卫**，属于强制工程规范

2. 通用工程优先双重守卫，兼顾兼容与效率

3. 严格规范宏命名，杜绝全局宏冲突

4. 禁止不写守卫的裸头文件入库工程
