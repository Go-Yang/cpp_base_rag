# 头文件未找到报错多级排查

## 一、前言

```text
fatal error: xxx.h: No such file or directory
```

这是预处理阶段最常见的致命错误。文件名存在、路径看起来正确，仍然可能报错，原因通常在**包含形式、搜索路径、大小写、工作目录、工具链/sysroot**。

核心总纲：**双引号先看当前文件目录，尖括号看 -I 和系统目录；找不到就逐级检查搜索路径和文件身份。**

## 二、包含形式与搜索顺序

### 1. 双引号

```c
#include "my_header.h"
```

GCC 的搜索顺序（简化）：

1. 包含该指令的源文件所在目录；
2. `-iquote` 指定的目录；
3. `-I` 指定的目录；
4. 系统目录（含 `-isystem`）。

### 2. 尖括号

```c
#include <stdio.h>
```

搜索顺序：

1. `-I` 指定的目录；
2. `-isystem`/系统目录。

**尖括号不搜索当前源文件目录**（除非该目录恰好通过 `-I` 加入）。

### 3. 常见误区

- 自定义头文件用 `<>`，然后抱怨找不到：改用 `""` 或把目录加入 `-I`；
- 以为 `-I` 只对 `<>` 生效：`-I` 对两种形式都生效；
- 以为双引号会搜索整个工程：它只搜索当前文件目录，不是项目根目录。

## 三、五级排查

### 一级：文件名与拼写

- 大小写：Linux 的 ext4 区分大小写；macOS 默认 APFS 通常**不区分**；Windows 不区分；
- 后缀：`.h` / `.hpp` / `.hxx`；
- 多余空格、不可见字符；
- 文件名里的中文字符/特殊符号。

### 二级：相对路径

- `./`、`../` 层数是否正确；
- 相对路径是相对于**包含文件所在目录**，不是当前工作目录；
- 多级目录容易写错，建议统一通过 `-I` 引入根目录。

### 三级：编译参数

```bash
gcc main.c -I./include -I./third_party/include -o app
```

- `-I` 后的路径必须存在；
- `-I` 可以多次出现；
- `-isystem` 用于系统级第三方头文件（抑制部分警告）；
- Makefile/CMake 中路径可能因执行目录不同而失效。

### 四级：工作目录

- IDE/Make/CMake 的实际编译目录可能不是项目根目录；
- 相对 `-I` 路径会随工作目录变化；
- 排查：打印 `pwd`，或把 `-I` 改成绝对路径测试。

### 五级：工具链/sysroot/架构

- 交叉编译时，主机头文件 ≠ 目标头文件；
- 需要 `--sysroot`、`-isysroot` 或工具链自带路径；
- 32/64 位、不同架构的库/头文件可能混用；
- 工具链本身缺开发包（如 `libc6-dev`、`build-essential`）。

## 四、验证搜索路径

### 1. 看预处理器的实际搜索过程

```bash
gcc -E -v main.c -o /dev/null
```

输出中 `#include <...> search starts here:` 和 `End of search list.` 之间就是实际搜索目录。

### 2. 看头文件包含树

```bash
gcc -H main.c -o /dev/null
```

逐行显示包含了哪些头文件、来自哪里。

### 3. 生成依赖

```bash
gcc -M main.c        # 输出 make 格式依赖
gcc -MM main.c       # 忽略系统头文件
```

### 4. 注意

`gcc -print-search-dirs` 显示的是**程序/库**搜索目录，不是头文件搜索目录。查头文件用 `-E -v` 或 `-H`。

## 五、常见场景

### 1. 自定义头文件用尖括号

```c
#include <my_header.h>   // 找不到
#include "my_header.h"   // 正确，或 -I 指向所在目录
```

### 2. 多级目录

文件在 `project/include/module/test.h`：

```c
#include "module/test.h"     // 需要 -Iproject/include
// 或
#include "test.h"           // 需要 -Iproject/include/module
```

### 3. Windows 正常、Linux 报错

大小写不一致。统一小写命名，或修正包含名。

### 4. 文件存在但权限不足

编译器读不到会报找不到。检查文件权限和目录执行权限。

### 5. 符号链接/大小写/同一文件多路径

可能导致找不到或 include guard 失效。统一路径和命名。

### 6. 交叉编译

确认使用的是目标工具链，而不是主机 gcc；检查 sysroot 中的头文件。

## 六、工程规范

1. 系统头文件用 `<>`，项目头文件用 `""`；
2. 项目头文件统一放 `include/`，通过 `-I` 引入根目录；
3. 包含路径写相对于包含根的形式，避免大量 `../`；
4. 文件名统一小写、无空格、无中文；
5. 跨平台项目在 CI 中用 Linux 大小写敏感环境验证；
6. 交叉编译显式配置 sysroot/toolchain file；
7. 用 `-H`/`-E -v` 排查搜索路径。

## 七、面试简答

### 1. `#include "..."` 和 `<...>` 的区别？

双引号先搜索当前源文件目录，再搜索 `-iquote`/`-I`/系统目录；尖括号只搜索 `-I` 和系统目录，不搜索当前文件目录。

### 2. 头文件明明存在为什么找不到？

常见原因：包含形式错误、大小写不匹配、相对路径层级错误、`-I` 未添加、工作目录不对、交叉编译 sysroot 不对、权限不足。

### 3. 如何查看 GCC 实际的头文件搜索路径？

`gcc -E -v main.c` 查看搜索列表；`gcc -H main.c` 查看包含树。`-print-search-dirs` 不是查头文件的。

### 4. 为什么 Windows 能编译、Linux 报错？

Windows 文件系统通常大小写不敏感，Linux 区分大小写。包含名与实际文件名大小写不一致时，Linux 找不到。

## 八、极简口诀

**双引先本地，尖括看 -I；**

**搜索路径 -E -v，包含树用 -H；**

**大小写、层级、工作目录，逐级排查；**

**交叉编译看 sysroot，权限也要查。**
