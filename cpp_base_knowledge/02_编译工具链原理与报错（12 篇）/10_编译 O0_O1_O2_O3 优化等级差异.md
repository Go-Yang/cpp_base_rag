# 编译 O0/O1/O2/O3 优化等级差异

## 一、前言

GCC 提供多个优化等级。它们改变的是**生成代码的方式**，不是语言语义：

- `-O0`：基本不优化，便于调试；
- `-O1`：基础优化；
- `-O2`：常用发布级别；
- `-O3`：更激进的优化；
- `-Os`：优化体积；
- `-Og`：面向调试的优化；
- `-Ofast`：`-O3` + 不安全的浮点优化。

核心总纲：**优化只对"行为已定义"的程序保持语义。** 如果代码有 UB、数据竞争或越界，任何优化等级都可能出问题，O0 只是碰巧没暴露。

## 二、各等级做什么

### 1. -O0

- 基本不做优化；
- 变量通常放在栈上，便于调试；
- 但**仍然使用寄存器**做临时计算和参数传递；
- 代码体积大、速度慢；
- 适合调试、复现问题。

### 2. -O1

- 删除明显冗余；
- 基础常量传播、死代码消除；
- 简单的寄存器分配和指令调度；
- 编译快，风险低。

### 3. -O2

- 在 O1 基础上启用更多优化；
- 函数内联（有限的）、循环优化、公共子表达式消除、指令调度；
- 不做最激进的循环变换/向量化扩展；
- 工业界常用发布级别。

### 4. -O3

- 更强的内联、循环展开、向量化、跨函数优化；
- 代码体积可能增大；
- 对 UB 的暴露更明显；
- 性能不一定总比 O2 高（取决于 workload）。

### 5. -Os / -Og / -Ofast

- `-Os`：优先减小代码体积，关闭部分增大体积的优化；
- `-Og`：保留调试体验的同时做温和优化（GCC 推荐调试用）；
- `-Ofast`：`-O3` + `-ffast-math`，允许不符合 IEEE 的浮点优化（可能改变数值结果），不要用于需要严格浮点语义的代码。

## 三、优化与调试

- `-g` 生成调试信息；可以与任意优化等级组合；
- 高优化等级下，变量可能被优化掉、行号可能跳变、内联导致调用栈变化；
- 调试发布版：`-O2 -g` + `-fno-omit-frame-pointer`；
- 精确定位：`-O0` 或 `-Og` 复现。

## 四、优化与未定义行为

优化器可以假设程序没有 UB。常见 UB：

- 有符号整数溢出；
- 越界访问；
- 解引用空/悬空指针；
- 未初始化读取；
- 严格别名违规；
- 数据竞争；
- 无限循环没有副作用（C++ 的 forward progress 规则）。

这些在 O0 可能"看起来正常"，在 O2/O3 下被优化暴露。

### 常见错误归因

| 现象 | 错误归因 | 正确解释 |
|---|---|---|
| O0 正常、O2 崩溃 | "O2 有 bug" | 通常是 UB 被暴露 |
| 变量在 gdb 里看不到 | "编译器坏了" | 变量被优化/放寄存器，用 -Og 或看汇编 |
| O3 报非法指令 | "O3 自动开新指令集" | 不会；需要 -march/-mavx 等显式开启 |
| O2 类型检查报错 | "优化导致类型错误" | 类型检查在优化前，通常是选项/宏/版本差异 |

## 五、平台/指令集

- `-O3` **不会自动启用**目标不支持的指令集；
- 指令集由 `-march=`、`-mtune=`、`-mavx*`、`-msse*` 等控制；
- 跨平台发布时，用基线指令集（如 `-march=x86-64`）保证兼容；
- 为特定 CPU 优化时，确保运行环境支持。

## 六、怎么选

| 场景 | 建议 |
|---|---|
| 开发调试 | `-O0 -g` 或 `-Og -g` |
| 通用发布 | `-O2` |
| 性能敏感 | `-O2` 先测，`-O3` 对比 |
| 体积敏感 | `-Os` |
| 数值严格 | 避免 `-Ofast`/`-ffast-math` |
| CI | 用发布选项跑测试，提前暴露 UB |

## 七、验证优化问题

1. 用 `-O0` 和 `-O2` 各跑一遍，确认是否只在优化下出现；
2. 用 UBSan/ASan/TSan 查 UB/数据竞争；
3. 用 `-S` 对比汇编；
4. 用 `-fno-strict-aliasing`、`-fwrapv` 等临时验证特定 UB；
5. 不要用 `volatile` 修数据竞争，用原子/锁。

## 八、面试简答

### 1. O0/O1/O2/O3 的区别？

O0 基本不优化，便于调试；O1 基础优化；O2 启用常用优化，工业界发布常用；O3 更激进（内联、循环展开、向量化），性能和体积 tradeoff 更大。优化只保持已定义行为的语义。

### 2. 为什么 O0 正常、O2 崩溃？

代码存在未定义行为（越界、悬空、数据竞争、有符号溢出等），O0 碰巧表现正常，O2 重排/删除/内联后暴露。根本是代码问题，不是优化 bug。

### 3. O3 会自动启用 AVX 等指令集吗？

不会。指令集由 `-march`/`-mavx` 等显式控制。O3 只是更激进的通用优化。

### 4. -Ofast 有什么风险？

它包含 `-ffast-math`，允许不符合 IEEE 的浮点优化（重排、假设无 NaN/Inf），可能改变数值结果，不适合需要严格浮点语义的代码。

## 九、极简口诀

**O0 好调试，O1 清冗余；**

**O2 发布常用，O3 更激进；**

**优化不造 UB，只把它暴露；**

**指令集看 -march，O3 不自动开。**
