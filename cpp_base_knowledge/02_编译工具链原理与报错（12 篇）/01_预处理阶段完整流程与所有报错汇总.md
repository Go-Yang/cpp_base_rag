# 预处理阶段完整流程与所有报错汇总

## 一、前言

预处理是编译的第一阶段，输入源文件，输出一个不再包含预处理指令的翻译单元（通常写成 `.i` 文件）。

核心总纲：**预处理只做 token 级文本处理：接行、删注释、展开宏、包含头文件、裁剪条件分支。** 它不理解类型、作用域和函数，所以预处理阶段的报错都是"文本/指令"层面的问题。

## 二、标准处理流程

### 1. 行接续与字符处理

- 处理反斜杠 `\` 续行：把行尾 `\` 和换行删除，与下一行拼接；
- 统一换行符；
- 处理源字符集/执行字符集（实现相关）。

### 2. 删除注释

- `//` 到行尾；
- `/* ... */` 块注释（不可嵌套）；
- 注释被替换为一个空格，避免 token 粘连。

### 3. token 化

把代码切成预处理 token：标识符、数字、字符串、字符常量、运算符、标点、头文件名等。

### 4. 执行预处理指令

按顺序处理：

- `#include`：递归包含头文件；
- `#define` / `#undef`：定义/取消宏；
- `#if` / `#ifdef` / `#ifndef` / `#elif` / `#else` / `#endif`：条件编译；
- `#error` / `#warning`：诊断；
- `#pragma`、`#line`：编译器控制。

### 5. 宏展开

- 对象宏替换；
- 函数宏参数预扫描、替换、重扫描；
- `#` 字符串化、`##` token 拼接；
- 禁止自递归（涂蓝）。

### 6. 输出 .i

```bash
gcc -E app.c -o app.i
g++ -E app.cpp -o app.ii
```

`.i` 文件是排查宏、头文件、条件编译问题的第一手材料。

## 三、预处理阶段的报错分类

### 1. 头文件相关

#### fatal error: xxx.h: No such file or directory

根因：

- 文件名拼写/大小写错误；
- 自定义头文件用了 `<>`，不搜索当前文件目录；
- 路径未通过 `-I`/`-iquote`/`-isystem` 加入；
- 相对路径层数错误；
- 交叉编译 sysroot 不匹配。

修复：检查包含形式、`-I` 路径、文件名大小写、工作目录。

#### #include nested too deeply

根因：

- 头文件循环包含且没有守卫；
- 嵌套层级确实过深。

修复：加 include guard/`#pragma once`；用前置声明/拆分头文件打破循环。

### 2. 宏相关

#### macro argument missing / unterminated argument list

根因：宏调用括号不匹配、参数个数不足、参数中有未保护的逗号。

#### pasting "..." and "..." does not give a valid preprocessing token

根因：`##` 拼接结果不是合法 token（如数字开头、标点拼接）。

#### 宏展开后语法错误

预处理本身可能不报错，展开后的代码在编译阶段报错。根因：

- 参数/整体缺括号；
- 多行宏续行符后带空格；
- 宏参数副作用；
- 宏体中的逗号/分号问题。

排查：`gcc -E` 查看展开结果。

### 3. 条件编译相关

#### #endif without #if / unterminated conditional directive

根因：`#if`/`#ifdef` 与 `#endif` 不配对、嵌套错乱、漏写 `#endif`。

#### #elif without #if / #else without #if

根因：条件块起始指令缺失或位置错误。

#### 宏未定义导致分支被误裁

`#ifdef` 拼写错误、宏未通过 `-D` 定义、头文件没包含。用 `-E` 查看最终保留的代码。

### 4. 诊断指令

#### #error

代码主动终止编译，通常用于平台/配置校验。按提示修正宏或环境。

#### #warning

输出警告，不终止编译（GCC 扩展，C23 标准化）。

### 5. 字符/编码相关

#### invalid character / stray '\' / invalid multibyte character

根因：全角符号、中文标点、不可见字符、编码不一致（GBK/UTF-8 混用）、孤立的反斜杠。

修复：统一 UTF-8，清理非法字符，检查续行符。

### 6. 注释相关

#### unterminated comment

块注释没有闭合，或注释嵌套导致提前闭合/吞掉代码。C/C++ 块注释不能嵌套。

## 四、容易误判为预处理的错误

| 报错 | 实际阶段 |
|---|---|
| `multiple definition of 'x'` | 链接期（不是预处理） |
| `undefined reference to 'x'` | 链接期 |
| `redefinition of 'struct X'` | 编译期（重复包含导致，但报错在编译） |
| `syntax error` | 编译期（可能是宏展开导致） |
| `cannot find -lfoo` | 链接期 |

宏展开导致的语法错误，**报错发生在编译期，根因在预处理**，排查要看 `.i`。

## 五、排查命令

| 目的 | 命令 |
|---|---|
| 输出预处理结果 | `gcc -E app.c -o app.i` |
| 不输出行标记 | `gcc -E -P app.c` |
| 查看所有预定义宏 | `gcc -dM -E - < /dev/null` |
| 查看头文件搜索过程 | `gcc -E -v app.c` |
| 只做语法检查 | `gcc -fsyntax-only app.c` |
| 查看宏展开 | `gcc -E app.c | grep ...` |

## 六、工程规范

1. 头文件加守卫，自包含；
2. 宏参数/整体加括号，避免副作用；
3. 多行宏 `\` 行尾无空格；
4. 条件编译缩进/注释，保证配对；
5. 统一编码和换行；
6. 用 `-I` 管理头文件路径，不用相对路径硬编码；
7. 构建时开启 `-Wall -Wextra`，把可疑写法尽早暴露。

## 七、面试简答

### 1. 预处理阶段做了什么？

处理行接续、删除注释、token 化、执行 `#include`/`#define`/条件编译等指令、展开宏，输出不含预处理指令的翻译单元。

### 2. `multiple definition` 是预处理错误吗？

不是。它是链接期错误：同一个强符号在多个目标文件/库中被定义。预处理只负责文本展开，不负责符号合并。

### 3. 宏展开后报语法错误怎么排查？

用 `gcc -E` 生成 `.i` 文件，查看宏展开后的真实代码，检查括号、分号、逗号、续行符和副作用。

### 4. 头文件循环包含怎么解决？

加 include guard 防止无限递归；用前置声明、把依赖下沉到 `.cpp`、拆分公共头文件来消除循环。

## 八、极简口诀

**预处理接行删注释，include 粘、define 换；**

**条件编译裁分支，error 停、warning 提；**

**宏错要看 .i 文件，多重定义是链接期；**

**头文件加守卫，路径用 -I。**
