# 跨平台编译语法兼容问题

## 一、前言

"本地能编译、换平台就报错"通常不是随机问题，而是以下差异：

- 数据模型（`long`、指针大小）；
- `char` 的有符号性；
- 对齐/字节序；
- 编译器对标准的支持；
- 平台 API/头文件；
- 文件系统大小写/换行。

核心总纲：**不要假设类型宽度、对齐、API 和文件系统行为；用固定宽度类型、标准库和显式平台封装。**

## 二、数据模型

| 模型 | 平台 | int | long | 指针 |
|---|---|---|---|---|
| ILP32 | 32 位 | 4 | 4 | 4 |
| LP64 | Linux/macOS 64 位 | 4 | 8 | 8 |
| LLP64 | Windows 64 位 | 4 | **4** | 8 |

- `long` 在 Windows 64 位是 4 字节，不要假设它总是 8；
- 需要固定宽度时用 `<stdint.h>`：`int32_t`、`int64_t`、`uint32_t`、`uint64_t`；
- 表示大小/下标用 `size_t`，指针差用 `ptrdiff_t`；
- `printf` 格式符要与类型匹配：`PRId64`、`PRIu64`（`<inttypes.h>`）。

```c
int64_t x = 0;
printf("%" PRId64 "\n", x);
```

## 三、char 的有符号性

- `char` 的符号由实现定义：x86 通常 signed，ARM 常 unsigned；
- 用于数值时显式写 `signed char` / `unsigned char`；
- 用于字符时用 `char`；
- 不要依赖 `char` 的取值范围做位运算/比较。

## 四、对齐与结构体

- 不同平台/ABI 的默认对齐不同；
- 结构体大小可能不同，不能直接按内存布局做协议传输；
- 协议/文件格式用显式序列化（字段逐个读写），或 `#pragma pack(1)`（注意未对齐访问）；
- ABI 公开结构体不要随意改字段顺序。

## 五、字节序

- x86/ARM 小端，部分嵌入式/网络协议大端；
- 网络字节序转换：`htons`/`htonl`/`ntohs`/`ntohl`；
- 不要用 `memcpy` 直接把多字节整数按内存布局解析，除非确认字节序。

## 六、标准与编译器差异

- C 标准：C89/C99/C11/C17/C23，不同编译器默认标准不同；
- C++ 标准：C++11/14/17/20/23，特性和库支持不同；
- GCC/Clang/MSVC 的诊断、扩展、ABI 不同；
- 用 `-std=` 显式指定标准，避免依赖编译器默认；
- 避免编译器扩展（`__attribute__`、`__int128`、VLA）或做条件封装。

## 七、平台 API 与头文件

| 功能 | Windows | POSIX/Linux |
|---|---|---|
| 睡眠 | `Sleep` | `usleep`/`nanosleep` |
| 时间 | `GetTickCount` | `clock_gettime` |
| 字符串比较 | `stricmp` | `strcasecmp` |
| 文件 | `CreateFile` | `open` |
| 动态库 | `LoadLibrary` | `dlopen` |

跨平台代码应封装统一接口，而不是在业务代码里 `#ifdef` 散落。

## 八、文件系统与文本

### 1. 大小写

- Linux ext4 区分大小写；
- Windows 不区分；
- macOS 默认 APFS **通常不区分大小写**（可配置为区分）；
- 包含文件名大小写要与实际一致，避免"Windows 能编、Linux 报错"。

### 2. 换行

- Windows `CRLF`，Linux `LF`；
- GCC 能处理 CRLF，但多行宏 `\` 后如果跟 `\r` 可能影响续行；
- 统一 LF 和 UTF-8，减少工具链差异。

### 3. 路径分隔符

- Windows `\`，POSIX `/`；
- 可移植代码用 `/`（Windows 也接受），或用平台 API 拼接。

## 九、交叉编译

- 使用目标工具链（`aarch64-linux-gnu-gcc` 等）；
- 配置 sysroot，确保头文件/库是目标架构；
- 不要混用主机库和目标库；
- 用 CMake toolchain 文件固定编译器/sysroot/find root path。

## 十、排查流程

1. 确认目标平台的数据模型（`long`/指针）；
2. 检查固定宽度类型和格式符；
3. 检查 `char` 符号性、字节序、对齐；
4. 检查平台 API 和头文件；
5. 检查文件名大小写、换行、编码；
6. 用目标工具链/容器复现，而不是"猜"。

## 十一、面试简答

### 1. 为什么 `long` 在 Windows 64 位是 4 字节？

Windows 使用 LLP64 数据模型，`long` 保持 32 位以兼容 Win32 API；Linux/macOS 使用 LP64，`long` 是 64 位。

### 2. 跨平台怎么保证整数宽度？

用 `<stdint.h>` 的 `int32_t`/`int64_t` 等固定宽度类型；大小/下标用 `size_t`；格式符用 `<inttypes.h>` 的宏。

### 3. 为什么结构体不能直接跨平台传输？

对齐/字节序/数据模型不同，结构体布局可能不同。应显式序列化字段，或使用统一的协议格式。

### 4. macOS 文件系统区分大小写吗？

默认 APFS 通常不区分大小写（但保留大小写），可以配置为区分。不要依赖大小写不敏感，包含名与实际文件名保持一致。

## 十二、极简口诀

**数据模型先确认，long 平台不一样；**

**固定宽度用 stdint，格式符用 inttypes；**

**对齐字节序显式化，协议不要直接 memcpy；**

**API 封装平台层，交叉编译看 sysroot。**
