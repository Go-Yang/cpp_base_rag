# 动态库运行时加载与卸载流程

## 一、前言

除了程序启动时由动态链接器自动加载依赖，程序还可以在运行时手动加载共享库：`dlopen` / `dlsym` / `dlclose`。这是插件系统、热更新、按需加载的基础。

核心总纲：**dlopen 加载并初始化库，dlsym 查找符号，dlclose 减引用计数。** 符号查找、构造/析构、作用域和卸载时机都有坑。

## 二、dlopen：加载共享库

### 1. 基本用法

```c
#include <dlfcn.h>

void* handle = dlopen("./libplugin.so", RTLD_NOW | RTLD_LOCAL);
if (!handle) {
    fprintf(stderr, "dlopen failed: %s\n", dlerror());
    return -1;
}
```

链接时需要 `-ldl`（glibc 2.34 之前；新版本符号已并入 libc，但加 `-ldl` 仍兼容）。

### 2. 常用 flags

| flag | 含义 |
|---|---|
| `RTLD_LAZY` | 函数符号惰性解析 |
| `RTLD_NOW` | 加载时解析全部符号（推荐，早暴露问题） |
| `RTLD_LOCAL` | 符号不进入全局作用域（默认） |
| `RTLD_GLOBAL` | 符号加入全局作用域，后续库可解析 |
| `RTLD_NODELETE` | dlclose 时不真正卸载（保留符号） |
| `RTLD_NOLOAD` | 不加载，只查询是否已加载 |
| `RTLD_DEEPBIND` | 优先在自身依赖中查找（glibc 扩展） |

常用组合：`RTLD_NOW | RTLD_LOCAL`。

### 3. 路径查找规则

- 路径包含 `/`：直接按路径加载；
- 不含 `/`：按动态链接器的搜索路径查找（RUNPATH/RPATH、`LD_LIBRARY_PATH`、`ld.so.cache`、默认目录）；
- `dlopen(NULL, ...)`：返回主程序句柄，用于 `dlsym` 查主程序符号（需 `-rdynamic` 导出）。

### 4. 加载时发生了什么

1. 检查是否已加载（按 inode/路径去重）；
2. 找到文件并映射；
3. 递归加载依赖；
4. 完成重定位（`RTLD_NOW` 时解析全部符号）；
5. 执行该库的构造器（`.init_array`），依赖库先于本库；
6. 返回句柄。

## 三、dlsym：查找符号

### 1. 基本用法

```c
typedef int (*plugin_init_fn)(const char*);
plugin_init_fn init = (plugin_init_fn)dlsym(handle, "plugin_init");
if (!init) {
    fprintf(stderr, "dlsym failed: %s\n", dlerror());
}
```

注意：`dlerror()` 会清除错误状态，调用前先清一次，失败后再取。

### 2. 特殊句柄

- `RTLD_DEFAULT`：按全局作用域查找，等价于默认符号解析；
- `RTLD_NEXT`：查找当前库之后的下一个定义，常用于包装/拦截（`LD_PRELOAD`）。

### 3. C++ 名字修饰

`dlsym` 按**原始符号名**查找。C++ 函数经过 name mangling，必须用 `extern "C"` 导出：

```cpp
extern "C" int plugin_init(const char* config);
```

否则需要传入 mangled 名（`_Z11plugin_initPKc`），非常脆弱。

## 四、dlclose：卸载共享库

### 1. 引用计数

- 每个库维护加载引用计数；
- `dlopen` 成功一次加一，`dlclose` 减一；
- 计数归零时，执行析构器，可能 `munmap` 卸载；
- 同一路径多次 `dlopen` 共享同一个映射。

### 2. 卸载时发生了什么

1. 引用计数减一；
2. 归零时执行该库的析构器（`.fini_array`）；
3. 解除映射（不一定立即，取决于实现和 flags）；
4. 清理符号表项。

### 3. 可能不卸载

- `RTLD_NODELETE`；
- 库使用了静态 TLS（`__thread`）——glibc 可能保留；
- 存在无法解析的依赖关系；
- 某些平台/实现不保证真正 unload。

所以不要假设 `dlclose` 后库的代码和数据一定失效；但也不要继续使用已 close 的句柄。

## 五、构造器与析构器

```c
__attribute__((constructor))
static void plugin_load(void) {
    // dlopen 时执行
}

__attribute__((destructor))
static void plugin_unload(void) {
    // dlclose 引用归零时执行
}
```

C++ 全局对象的构造/析构同理。**不要在构造器里依赖主程序的全局状态**：插件加载时机不确定，主程序可能已初始化或尚未初始化。

## 六、符号作用域与冲突

### 1. RTLD_LOCAL vs RTLD_GLOBAL

- `RTLD_LOCAL`：插件符号自成一域，多个插件可以各自导出同名符号，互不干扰；
- `RTLD_GLOBAL`：符号加入全局作用域，后续加载的库可解析，但容易与已有符号冲突；
- 插件系统默认用 `RTLD_LOCAL`，除非明确需要共享符号。

### 2. 插件之间共享类型

如果插件 A 和插件 B 需要交换对象：

- 通过主程序提供的 C 接口；
- 保证 ABI 一致；
- 避免各自静态链接不同的 C++ 运行库，否则 `std::string`/异常/RTTI 跨边界会出问题。

### 3. 静态 TLS 问题

插件使用 `__thread` / `thread_local` 静态 TLS 时，如果在主线程启动后 `dlopen`，可能报：

```text
cannot allocate memory in static TLS block
```

解决：启动时预先 `LD_PRELOAD`，或直接链接该库，或改用动态 TLS 模型。

## 七、完整插件示例

```c
// plugin.h
typedef struct {
    const char* name;
    int (*init)(void);
    void (*fini)(void);
} Plugin;

// plugin.c
#include "plugin.h"

static int my_init(void) { return 0; }
static void my_fini(void) { }

__attribute__((visibility("default")))
Plugin plugin_entry = {
    .name = "demo",
    .init = my_init,
    .fini = my_fini,
};
```

```c
// host.c
void* h = dlopen(path, RTLD_NOW | RTLD_LOCAL);
Plugin* p = (Plugin*)dlsym(h, "plugin_entry");
if (p && p->init() == 0) {
    // 使用插件
}
p->fini();
dlclose(h);
```

## 八、常见报错与排查

### 1. dlopen 返回 NULL

```text
libplugin.so: cannot open shared object file: No such file or directory
libplugin.so: undefined symbol: xxx
```

用 `dlerror()` 打印具体原因；用 `ldd libplugin.so` 检查依赖；用 `LD_DEBUG=libs,symbols` 跟踪。

### 2. dlsym 返回 NULL

- 符号没导出（`-fvisibility=hidden`）；
- C++ 名字未 `extern "C"`；
- 符号被 version script 隐藏；
- 句柄不对或库已卸载。

```bash
objdump -T libplugin.so | grep plugin_entry
nm -D libplugin.so | grep plugin_entry
```

### 3. dlclose 崩溃

- 仍有代码/数据指针指向已卸载库；
- 析构器访问了已释放的资源；
- 插件注册的回调没注销。

修复：确保所有回调在 `dlclose` 前注销；必要时用 `RTLD_NODELETE` 避免卸载。

### 4. 插件符号互相干扰

默认 `RTLD_LOCAL` 可以隔离；若必须 `RTLD_GLOBAL`，给符号加插件前缀。

### 5. 静态 TLS 分配失败

见上文，预加载或改用动态 TLS。

## 九、调试命令

| 目的 | 命令 |
|---|---|
| 查看导出符号 | `objdump -T libplugin.so` |
| 查看依赖 | `ldd libplugin.so` |
| 跟踪加载/符号 | `LD_DEBUG=libs,symbols ./host` |
| 查看已加载库 | `cat /proc/<pid>/maps` |
| gdb 查看加载库 | `info sharedlibrary` |
| 查找符号归属 | `dladdr(ptr, &info)` |
| 检查版本脚本 | `readelf -V libplugin.so` |

## 十、预防规范

1. 插件入口统一用 `extern "C"` 和明确的前缀。
2. `dlopen` 优先 `RTLD_NOW | RTLD_LOCAL`，尽早暴露问题并隔离符号。
3. 插件与主程序通过 C 接口交互，不跨边界传递复杂 C++ 对象。
4. 所有注册的回调在卸载前注销。
5. 插件依赖的库路径用 RUNPATH 固定，不依赖运行环境。
6. 不要在构造器里依赖主程序状态；用显式 `init` 函数。
7. 需要真正卸载时，避免 `RTLD_NODELETE` 和静态 TLS。

## 十一、面试标准简答

### 1. dlopen 的 RTLD_NOW 和 RTLD_LAZY 有什么区别？

`RTLD_NOW` 在加载时解析全部符号，缺失立即报错；`RTLD_LAZY` 只解析数据符号，函数符号第一次调用时才解析，启动快但问题暴露晚。

### 2. 为什么 dlsym 找不到符号？

常见原因：C++ 名字被 mangling（没有 `extern "C"`）、符号被编译器的 visibility 隐藏、version script 限制导出、库版本不对。用 `objdump -T`/`nm -D` 确认导出。

### 3. dlclose 会立即卸载库吗？

不保证。它只递减引用计数，归零时才执行析构并可能解除映射。`RTLD_NODELETE`、静态 TLS、依赖关系等都可能导致库保留在内存中。

### 4. RTLD_LOCAL 和 RTLD_GLOBAL 的区别？

`RTLD_LOCAL` 让库的符号只对通过该句柄查找可见，不与全局作用域冲突；`RTLD_GLOBAL` 把符号加入全局作用域，后续加载的库可以解析它们，但也更容易产生同名冲突。

## 十二、极简口诀

**dlopen 加载跑构造，dlsym 按名找符号；**

**C++ 要 extern "C"，隐藏符号找不到；**

**RTLD_NOW 早暴露，RTLD_LOCAL 少冲突；**

**dlclose 减引用，归零才析构。**
