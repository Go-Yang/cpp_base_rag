# 进程权限、内存保护机制

## 一、前言

进程安全有两层：

1. **权限层**：这个进程能以谁的身份做事（UID/GID、capabilities）；
2. **内存保护层**：这个进程能对哪些内存做什么（读/写/执行）。

核心总纲：**权限决定"能不能碰"，页表权限决定"能不能读/写/执行"。** 两层都绕过，才叫真正的权限提升。

## 二、进程身份与权限

### 1. 三种 UID

| UID | 含义 |
|---|---|
| real UID | 启动进程的真实用户 |
| effective UID | 内核做权限检查时使用的身份 |
| saved UID | 用于在特权/非特权之间切换 |

同理有 real/effective/saved GID。

### 2. setuid / setgid

- 文件设置 setuid 位后，执行时进程的 effective UID 变为文件属主；
- 典型例子：`/usr/bin/passwd` 需要写 `/etc/shadow`；
- setuid root 程序风险极高，任何漏洞都可能变成 root 提权。

安全限制：setuid 程序运行时进入 **secure-execution mode**：

- 忽略 `LD_LIBRARY_PATH`、`LD_PRELOAD` 等危险环境变量；
- 只从受信路径加载库；
- `AT_SECURE` 辅助向量标记为 1。

### 3. capabilities

把 root 权限拆成细粒度能力：

| capability | 作用 |
|---|---|
| `CAP_NET_BIND_SERVICE` | 绑定 1024 以下端口 |
| `CAP_SYS_ADMIN` | 大量管理操作（近似 root） |
| `CAP_SYS_PTRACE` | ptrace 其他进程 |
| `CAP_DAC_OVERRIDE` | 绕过文件权限检查 |
| `CAP_SYS_TIME` | 修改系统时间 |

```bash
capsh --print
getcap ./app
sudo setcap cap_net_bind_service=+ep ./app
```

capabilities 比 setuid root 更小权限，但仍需谨慎授予。

### 4. 其他权限机制

- `no_new_privs`：禁止 exec 后获得新权限（容器常用）；
- seccomp：限制可用的系统调用；
- namespaces：隔离 PID、网络、挂载、用户等；
- SELinux / AppArmor：强制访问控制（MAC）；
- Yama ptrace_scope：限制 ptrace 范围；
- `prctl(PR_SET_DUMPABLE, 0)`：禁止 core dump/ptrace。

## 三、虚拟内存权限

### 1. 页表权限位

每个页表项包含：

- 用户/超级用户位（U/S）：用户态能否访问；
- 读/写位（R/W）；
- 执行位（NX）；
- 存在位、访问位、脏位等。

用户态访问违规 → `SIGSEGV`。

### 2. 常见段的权限

| 区域 | 权限 |
|---|---|
| `.text` | r-x |
| `.rodata` | r-- |
| `.data` / `.bss` | rw- |
| 堆 | rw- |
| 栈 | rw- |
| vDSO | r-x |
| 未映射区 | --- |

```bash
cat /proc/<pid>/maps
```

### 3. mprotect

```c
mprotect(addr, len, PROT_READ | PROT_WRITE);
```

- 修改页权限，粒度是页；
- 可以把只读页临时改为可写（自修改代码）；
- 违反 W^X 的安全策略可能被拒绝；
- 失败返回 -1，errno 可能是 `EACCES`（文件映射不允许）、`ENOMEM`（区间无效）。

### 4. NX 与 W^X

- **NX（No-eXecute）**：数据页不可执行，阻止栈/堆上的 shellcode；
- **W^X**：同一页不能同时可写和可执行；
- JIT 需要先写再改权限：`mmap(RW)` → 写 → `mprotect(RX)`；
- 可执行栈由 `PT_GNU_STACK` 标记，链接时可用 `-z noexecstack` 强制。

```bash
readelf -l app | grep GNU_STACK
# 带 RWE 表示栈可执行，通常不应出现
```

## 四、RELRO：保护 GOT

GOT 存放动态符号地址，是劫持控制流的常见目标。

### 1. Partial RELRO（默认）

- 重定位后，部分 GOT 段设为只读；
- `.got.plt` 仍可写（惰性绑定需要）。

### 2. Full RELRO

```bash
gcc main.c -Wl,-z,relro,-z,now -o app
```

- 启动时完成全部符号绑定（`-z now`）；
- 之后整个 GOT 设为只读；
- 启动稍慢，但能阻止 GOT 覆盖攻击。

```bash
readelf -l app | grep GNU_RELRO
readelf -d app | grep BIND_NOW
```

## 五、栈保护与 FORTIFY

### 1. Stack Canary

编译器在返回地址前放置随机数，函数返回前校验：

```bash
gcc -fstack-protector-strong main.c -o app
```

被覆盖时触发 `__stack_chk_fail`，程序终止并打印 `stack smashing detected`。

### 2. FORTIFY_SOURCE

```bash
gcc -O2 -D_FORTIFY_SOURCE=2 main.c -o app
```

对 `memcpy`、`strcpy`、`sprintf` 等调用做编译期/运行期边界检查，能在溢出前终止。

### 3. 其他编译期保护

- `-fstack-clash-protection`：防栈冲突；
- `-fcf-protection=full`：Intel CET 控制流保护；
- `-D_GLIBCXX_ASSERTIONS`：C++ 容器断言；
- `-Wl,-z,noexecstack`：栈不可执行。

## 六、常见问题

### 1. 写 .text 崩溃

代码段是只读的，写入触发 `SIGSEGV`。需要修改代码时用 `mprotect`，并遵守 W^X。

### 2. mprotect 失败

- 区间未按页对齐；
- 区间包含未映射页；
- 文件映射不允许写（`MAP_SHARED` 只读）；
- 安全策略禁止可执行匿名映射。

用 `errno` 和 `/proc/<pid>/maps` 定位。

### 3. setuid 程序行为异常

secure-execution 模式下 `LD_LIBRARY_PATH` 被忽略，动态库必须放在受信路径，或者编译时设置 RPATH。

### 4. 普通用户无法 ptrace

`/proc/sys/kernel/yama/ptrace_scope` 限制了 ptrace 范围。调试自己启动的进程通常允许；attach 其他用户的进程需要权限。

### 5. Permission denied 与 EACCES

- 文件系统权限不足；
- capability 缺失；
- SELinux/AppArmor 拒绝；
- mount 为只读或 `noexec`。

用 `strace` 看具体系统调用和 errno。

## 七、排查命令

| 目的 | 命令 |
|---|---|
| 查看身份 | `id` |
| 查看 capabilities | `capsh --print` / `getcap app` |
| 查看文件权限 | `ls -l` / `getfacl` |
| 查看内存映射权限 | `cat /proc/<pid>/maps` |
| 查看 RELRO | `readelf -l app | grep GNU_RELRO` |
| 查看立即绑定 | `readelf -d app | grep BIND_NOW` |
| 查看栈可执行 | `readelf -l app | grep GNU_STACK` |
| 检查安全配置 | `checksec --file=app` |
| 跟踪权限失败 | `strace -e trace=openat,mmap,mprotect ./app` |

## 八、工程设计建议

1. 优先用 capabilities 代替 setuid root。
2. 服务进程降权：启动后 `setuid`/`setgid` 到低权限用户，保留最小 capability。
3. 默认开启 PIE、NX、RELRO、canary、FORTIFY。
4. 不要在可写内存上保留可执行权限；JIT 遵守 W^X。
5. 对不可信输入做边界检查，启用 ASAN 做测试。
6. 容器使用 `no_new_privs`、seccomp、只读挂载、最小 capability。
7. 定期用 `checksec` 审计二进制安全属性。

## 九、面试标准简答

### 1. real UID 和 effective UID 的区别？

real UID 是启动进程的用户身份；effective UID 是内核做权限检查时使用的身份。setuid 程序执行时 effective UID 变为文件属主，从而实现受控提权；saved UID 用于在两者间切换。

### 2. setuid 程序为什么忽略 LD_LIBRARY_PATH？

setuid 程序处于 secure-execution 模式，防止攻击者通过环境变量注入恶意库。动态链接器只从受信路径加载库，危险环境变量被忽略。

### 3. NX、ASLR、RELRO、canary 分别防什么？

NX 阻止数据页执行（防 shellcode）；ASLR 随机化地址（防硬编码跳转）；RELRO 保护 GOT（防 GOT 劫持）；canary 检测栈溢出（防返回地址覆盖）。

### 4. capabilities 和 root 的关系？

capabilities 把 root 的特权拆成独立能力。进程可以只授予所需的 capability（如绑定低端口），而不必拥有完整 root，降低被利用后的影响面。

## 十、极简口诀

**UID 管身份，页表管权限；**

**setuid 要慎用，capabilities 拆分权；**

**text 只读、栈不可执行，W^X 守内存；**

**RELRO 锁 GOT，canary 防溢出。**
